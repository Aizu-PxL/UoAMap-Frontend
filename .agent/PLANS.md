# UoAMap ExecPlan の規約

ExecPlan は、長時間・複数スライスにまたがる変更を、別スレッドからでも再開できるようにする生きた設計文書である。重要な機能追加またはリポジトリ横断リファクタリングでは、実装前にこの規約に従う ExecPlan を作成または更新する。

現在のリポジトリ横断リファクタリングでは [.agent/refactor-plan.md](refactor-plan.md) を使用する。

## 必須内容

ExecPlan は単体で理解できるよう、次を具体的なファイル名と検証方法つきで記載する。

1. 目的と期待する結果
2. 現在の構造と、問題を示すファイル単位の根拠
3. SCOPE と非目標
4. 維持する外部挙動・公開契約・データ契約
5. 依存関係を考慮した実装順序
6. 各マイルストーンの受入基準と検証コマンド
7. 日付つきの進捗ログ
8. 発見事項、判断、代替案と採否理由
9. 最終結果、未解決事項、残存リスク

## 実行規則

- ExecPlan は複数スライスの上位計画とし、実装は `docs/WORKFLOW.md` に従ってスライスごとに `docs/tasks/13x-*.md` を作る。
- 各スライスは、純粋ロジック、1つの依存境界、1コンポーネント程度のレビュー可能な単位にする。
- 各スライスで、ブリーフ作成、実装、検証、`docs/STATUS.md` とExecPlanの更新、独立した読み取り専用レビューまでを完了してから次へ進む。
- 小さな不明点はリポジトリの仕様・テスト・実装から解決し、判断をExecPlanへ記録する。
- 破壊的変更、外部挙動の変更、依存追加、SCOPEの実質的拡大、人間の業務判断が必要な場合だけ停止して確認する。
- 実装中に計画が誤っていると判明したら、根拠を記録して計画を更新する。古い記述を事実として残さない。
- 作業ツリーは常にビルド可能・レビュー可能に保つ。失敗を隠すためにテストや型検査を弱めない。
- `checkout`、`reset`、`stash`、`commit` は行わない。ブランチとコミットはユーザーが管理する。

## リファクタリング固有の制約

- 外部から観測可能な挙動を変更しない。
- URLルートと `at` / `to` / `focus` / `highlight` の意味・保持規則を維持する。
- 公開props、設定キー、Repository契約、データ形式、SVGの既存IDを維持する。
- `public/maps/*.svg` は `Route` グループ以外を変更しない。生成物を手編集しない。
- 必要性が立証されない依存追加・更新、無関係な一括整形、行数削減だけを目的にした抽象化をしない。
- 動的参照の可能性を確認せずにコードを削除しない。
- React管理DOMと `MapCanvas` の非管理SVG DOMを混在させない。
- UIを変更する場合は、先にFigmaと `docs/FIGMA.md` を確認する。構造変更だけなら見た目を変えない。

## 進捗の書き方

チェックボックスだけでなく、日付、変更したファイル、実行した検証、判断を短く追記する。停止時は「次に実行する具体的な1手」を必ず残す。

```text
- [x] 2026-07-22: URL更新ロジックを純粋関数へ抽出。bun test / build / verify:places PASS。
- [ ] 次: docs/tasks/13c-... のSCOPEを確認し、経路表示モデルのcharacterization testから開始する。
```
