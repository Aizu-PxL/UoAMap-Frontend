# WORKFLOW — 作業の進め方

最終更新: 2026-07-21
**位置づけ**: 誰(どのセッション・どのエージェント)が実装しても同じ手順・同じ品質になるための取り決め。手順の本体(ブリーフ様式・検証ゲート・SCOPE厳守・ドキュメント更新責任)は共通で、レビューとエスカレーションの回し方だけ実装者によって分かれる(下記「運用モード」)。仕様の正は [SPEC.md](SPEC.md)。

## 運用モード

- **Codex単独運用(基本)**: 実装セッションがブリーフ作成〜実装〜検証を進め、検証後に会話履歴を引き継がないレビュー専用サブエージェントを起動して、別コンテキストの読み取り専用レビューを行う。実装セッションは指摘の反映・再検証・最終統合を担い、人間(ユーザー)はゴール提示・コミット・最終判断を担う。
- **Claude(Fable)が関与する場合**: グローバルの spec-translator 分業に戻る。Fable がブリーフを書いて実装を Codex に委譲し、実装とは別の読み取り専用セッションでレビュー、受入FAIL/レビュー指摘は実装者へ1回差し戻し、2回目の失敗や原因の特定できない問題はリードが直接引き取る。コミットはユーザーまたはリード。

## 作業開始時に読む順

1. [STATUS.md](STATUS.md) — 現在の進捗・動作確認手順・アーキテクチャ要点
2. [HANDOFF.md](HANDOFF.md) — 直近の完了内容・判断記録・次の着手候補
3. [SPEC.md](SPEC.md) — 着手する機能の仕様(正)
4. このファイル — 運用モードと品質ゲート
5. [BACKLOG.md](BACKLOG.md) — 次に着手する候補

## 全体の流れ

```
BACKLOG.md / SPEC.md ロードマップ
   │  (仕様が絡むならまずSPEC.mdを更新)
   ▼
ブリーフ作成: docs/tasks/NN-<slug>.md
   ▼
実装
   ▼
検証ゲート(下記を自分で実行)
   ▼
STATUS.md・検証結果を更新
   ▼
別セッションの読み取り専用レビュー
   ▼
コミット(ユーザーまたはリード)
```

複数スライスをまとめて進める場合も、スライスごとにこの1周を回す(ブリーフ→実装→検証→STATUS更新→レビュー)。スライスは1画面/1コンポーネント/1データ拡張の単位に小さく切る。

## ブリーフの書き方(docs/tasks/NN-<slug>.md)

`02a`〜`03b` が実例。Codex単独運用ではCodexが自分で切り、Claude関与時はFableが用意する。必須セクション:

- **GOAL**: 何がどうなれば完了か1段落
- **参照**: SPEC.mdの該当節、関係ファイル、前スライスからの引き継ぎ事項
- **やること**: 実装内容。コードの書き方(実装の詳細)は実装者の裁量
- **SCOPE**: 変更してよいファイルの明示列挙。**それ以外は触らない**
- **受入基準**: 機械的に確認できるチェックリスト(コマンド・表示されるべき要素)。実装者が自分で実行して結果を記録する
- **DELIVERABLE**: 変更ファイル一覧 + 受入結果(PASS/FAIL) + 設計判断の要約

番号はロードマップのステップに合わせる(ステップ3の続きなら `03c-...`)。

## 実装の約束

- SCOPE外のファイルを変更しない
- **git操作(checkout / reset / stash / commit)をしない**。コミットはユーザーまたはリードが行う
- 作業開始時に `git status --short` を確認し、SCOPE内外を問わず追跡済みファイルは `git diff HEAD -- <path>`、未追跡ファイルは直接確認して、ステージ済み・未ステージ・未追跡を含む既存差分の内容を読み取り専用で記録する。既存のユーザー変更と今回の変更をレビュー時に区別できる状態を保つ
- `public/maps/` のSVGは **Route グループの追加・編集のみ**可。既存要素・ID・座標系は読み取り専用
- 受入基準を自分で実行し、PASS/FAILを事実で報告する(推測で合格にしない)
- React管理DOMとSVG非管理DOMの境界(STATUS.md「アーキテクチャ要点」)を壊さない

## 検証ゲート(スライス完了の条件)

1. `bun run build` が通る(型チェック込み)
2. `bun run verify:places` が **36件PASS**(places.tsを触っていなくても実行する — 巻き戻し事故の検知のため)
3. ルート(`public/maps/` の Route グループ・`scripts/extract-routes.ts`・`src/features/routing/`)を触ったら `bun run verify:routes` と `bun test` も通す
4. ブラウザ確認: 幅402pxで STATUS.md の検証用URL表のうち関連するものを確認し、コンソールエラーがないことを確認する

## レビュー

- diff を **ブリーフ + SPEC.md に照合**する(仕様どおりか / SCOPE外に漏れていないか / 受入基準を実際に満たすか / 既存IDや境界を壊していないか)
- **Codex単独運用**: 検証ゲート後、実装セッションは `spawn_agent` を `fork_turns="none"` で呼び出し、会話履歴を持たないレビュー専用サブエージェントへ読み取り専用レビューを委ねる。対象ブリーフ、参照するSPEC節、SCOPE、受入基準、変更ファイル、作業開始時の既存差分、実行した検証コマンドとPASS/FAIL、ブラウザ確認のURL・幅・コンソール結果を明示し、`AGENTS.md` の「Review guidelines」に従わせる
- レビュー専用サブエージェントは、初回・再レビューとも `git status --short`、対象となる追跡済みファイルの `git diff HEAD -- <path>`、対象となる未追跡ファイルの直接確認により、ステージ済み・未ステージ・未追跡を含む最終変更全体を確認する。作業開始時スナップショットと最終状態を比較し、既存のユーザー変更そのものは指摘対象にせず、今回の作業による改変・消失やSCOPE外への追加変更を判定する
- レビュー専用サブエージェントはファイル変更、checkout / reset / stash / commit等の変更を伴うgit操作、外部送信を行わない。実装セッションはレビュー完了を待ち、結果を自分で確認して統合する
- レビュアーの出力は「指摘のみの簡潔なリスト(重要度付き・ファイル/行つき)」とし、指摘がなければその旨を明言させる。レビュアーはファイルを変更しない
- **Claude関与時**: 実装したセッションとは別の読み取り専用セッション(Codex read-only または新規スレッド)でレビューする。出力は「指摘のみの簡潔なリスト(重要度付き・箇所つき)」、指摘なしならそう明言
- 初回レビューの指摘は実装セッションへ1回だけ差し戻し、修正と関連する検証ゲートを再実行して、STATUS.mdと検証結果も更新する。修正後の最終diffを同じ条件で別コンテキストの再レビューへ1回渡す。再レビューで重要度や新旧を問わず対応可能な指摘が残った場合は追加修正へ進まず、レビュー未完了としてユーザーへエスカレーションする
- サブエージェントを起動できない、タイムアウト・異常終了した、対象差分を取得できない、または所定形式の結果を受領できない場合は自己レビューで代替しない。実行内容とエラー要約を付け、レビュー未完了としてユーザーへ報告する

## 差し戻しとエスカレーション

- 受入FAILやレビュー指摘は、エラー要約を付けて実装者へ**1回だけ**差し戻す(同じ指示を繰り返さない)
- **Claude関与時**: 2回目の失敗、および非同期・座標変換・状態管理の境界など1回の調査で原因が特定できない問題は、リードが直接修正する
- **Codex単独運用**: 同種の行き詰まり(2回目の失敗・原因不明の不具合・再レビューで対応可能な指摘が残る場合)は推測で進めず、状況を要約してユーザーに報告しエスカレーションする
- どちらのモードでも、手戻りの大きい判断(仕様の解釈、破壊的変更、SCOPEの拡大)は着手前にユーザーへ確認する
