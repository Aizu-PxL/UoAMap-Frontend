# WORKFLOW — 作業の進め方

最終更新: 2026-07-19
**位置づけ**: 誰(どのセッション・どのエージェント)が作業しても同じ手順・同じ品質になるための取り決め。

## 全体の流れ

```
BACKLOG.md / SPEC.md ロードマップ
   │  (仕様が絡むならまずSPEC.mdを更新)
   ▼
ブリーフ作成: docs/tasks/NN-<slug>.md
   ▼
実装(Codex等に委譲 or 直接実装)
   ▼
検証ゲート(下記)
   ▼
レビュー(実装とは別の読み取り専用セッション)
   ▼
STATUS.md 更新 → コミット
```

## ブリーフの書き方(docs/tasks/NN-<slug>.md)

02a〜02d が実例。必須セクション:

- **GOAL**: 何がどうなれば完了か1段落
- **参照**: SPEC.mdの該当節、関係ファイル、前提知識(前スライスからの引き継ぎ事項)
- **やること**: 実装内容。ただし「どう書くか」は実装者に委ねる(細かいコード指示をしない)
- **SCOPE**: 変更してよいファイルの明示列挙。**それ以外は触らない**
- **受入基準**: 機械的に確認できるチェックリスト(コマンド、表示されるべき要素)。実装者が自分で実行して結果を報告する
- **DELIVERABLE**: 報告フォーマット(変更ファイル一覧+受入結果+設計判断の要約)

番号はロードマップのステップに合わせる(ステップ3なら `03a-...`)。

## 実装者(Codex等)の約束

- SCOPE外のファイルを変更しない
- **git操作(checkout / reset / stash / commit)をしない**。コミットはユーザーまたはリードが行う
- `public/maps/` のSVGは読み取り専用
- 受入基準を自分で実行し、PASS/FAILを事実で報告する(推測で合格にしない)
- React管理DOMとSVG非管理DOMの境界(STATUS.md「アーキテクチャ要点」)を壊さない

## 検証ゲート(スライス完了の条件)

1. `bun run build` が通る(型チェック込み)
2. `bun run verify:places` が **36件PASS**(places.tsを触っていなくても実行する — 巻き戻し事故の検知のため)
3. ブラウザ確認: 幅402pxで STATUS.md の検証用URL表のうち関連するものを確認、コンソールエラーなし

## レビュー

- 実装したセッションとは**別の読み取り専用セッション**(Codex read-onlyまたは新規スレッド)で、diffをブリーフ+SPEC.mdに照合する
- 出力は「指摘のみの簡潔なリスト(重要度付き・箇所つき)」。指摘なしならそう明言
- 指摘の修正も原則実装側へ差し戻す

## 差し戻しとエスカレーション

- 受入FAILやレビュー指摘は、エラー要約を付けて実装者へ**1回だけ**差し戻す
- **2回目の失敗はリードが直接修正**する(同じ指示を繰り返さない)
- 非同期・座標変換・状態管理の境界など、原因が1回の調査で特定できない問題もリードが引き取る
