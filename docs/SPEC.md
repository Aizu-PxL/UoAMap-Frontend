# UoAMap 仕様書

最終更新: 2026-07-20(マップオーバーレイの固定サイズ計算を縦横比対応)

このドキュメントがプロダクト仕様の正。実装・デザイン・API設計はここに従う。
変更したくなったら、まずこのドキュメントを更新してから実装する。

## 1. プロダクト概要

会津大学オープンキャンパス(OC)の来場者(受験生・保護者)向けの**ルート案内Webアプリ**。

来場者は構内の地理に不案内で「向かうべき方向がわからない」。そこで:

1. **目的地をセットする** — アプリ内でイベントを選ぶ、または外部(チラシ・サイト等)に貼られたリンクを踏むと目的地がセットされた状態でアプリが開く
2. **現在地をセットする** — 会場各所に貼られたQRをスキャンする
3. **ルートが表示される** — 現在地から目的地までの進むべきルートが地図上に描かれる

これがコア体験。検索・スケジュール等はこの体験を支える周辺機能。

- **初回投入目標**: 2026年夏のオープンキャンパス
- **継続前提**: 翌年以降のOCでも使い回せるよう、年度データ(イベント・QR配置)を差し替え可能な設計にする
- **対象デバイス**: スマホ専用。320〜430px幅では画面サイズに追従して表示し、PC専用レイアウトは作らない

## 3. 機能仕様

### 3.1 地図表示

地図素材は自作の**構造化SVG**(`public/maps/`)。画像ではなくインラインSVGとして描画し、
要素ID単位のハイライト・ルート線の重畳・CSSテーマ適用を可能にする。

素材一覧(1ファイル = 1シート):

| ファイル | 内容 | 備考 |
|---|---|---|
| CampusMap | 屋外キャンパス全体図 | `building_*`(全建物)、`path_Pedestrian1..12`(歩行者路)、道路・駐車場・フィールド等のレイヤーあり |
| RQ1F / RQ2F / RQ3F | 研究棟 1〜3F | `room_*` 各66〜91室。東西棟(e/w)区分あり |
| SH1F / SH2F | 学生ホール 1〜2F | `room_*` あり |
| LH | 講義棟 | **1Fと2Fが1ファイルに併記**(`fill_1F` / `fill_2F`) |
| LICTiA1F | LICTiA 1F | `room_*`, `area_*` あり |
| UBIC | UBIC(単一フロア) | `room_*`, `area_*` あり |

- SVGは共通して `Frame`(外形)/ `Part` / `Room` / `Text` / `Mark`(階段等)のレイヤー構造を持つ
- 部屋は `room_<棟>_<用途>_<部屋番号>` 形式のIDを持ち(例: `room_e1_seminar10_133`)、**Placeとの紐付けはこのSVG要素IDで行う**
- 座標系は各SVGのviewBox座標をそのまま使う(別途の正規化はしない)
- 操作: パン・ズーム、シート切り替え(キャンパス全体 ⇄ 各建物)、建物内のフロア切り替え
- 地図上にイベント会場・現在地・目的地のマーカーを表示し、「特定地点へのフォーカス」をアプリ全体から呼び出せる
- **イベント開催地マーカー**: イベントが開催される地点(表示中フロアに属するもの)にマーカーを表示する。タップすると検索タブが開き、該当イベントカードが強調表示される(3.4)。同一地点に複数イベントがある場合はマーカーを1つに集約する。現在地・目的地・注目ピンと同じ地点ではイベントマーカーを省略し、該当ピンだけを表示する

#### 3.1.1 マップ内ビジュアル仕様(ラベル・マーカー)

地図SVGに焼き込まれた `<text>` はオーサリングツール由来のフォント指定(Meiryo UI)を持ち、
非Windows環境で明朝体にフォールバックする。また、ズーム(viewBox縮小)に比例して拡大する。
これを避けるため、**焼き込みテキストは表示に使わず、React側で再描画する**:

**ラベル(React再描画方式)**

- SVGロード時に `Text` レイヤーの `<text>`(`tspan` 含む)から文言・アンカー位置・元font-sizeを抽出し、元の `<text>` は非表示化する(SVG資産自体は変更しない)
- 専用ラベルレイヤー(route層とmarker層の間)に、アプリのフォントトークン(Noto Sans JP)で再描画する
- ラベルは**画面上で固定サイズ**とする。SVGの `preserveAspectRatio="xMidYMid meet"` に合わせ、ピンと同じ逆スケール方式
  (`user単位/px = max(viewBox.width / コンテナ幅, viewBox.height / コンテナ高さ)`)を使う。目標サイズは11〜13px程度
- **間引き**: 元font-sizeを重要度として使い、ズームアウト時(キャンパス全体など)は重要度の高いラベルのみ表示する。ズームインに応じて小さい部屋のラベルも出す
- 複数行ラベル(tspan複数)は1ラベルとして行間を再構成して描画する
- ピン・マーカーと同一アンカーのラベルは、マーカーと重ならないようアンカーの下側にオフセットして表示する

**マーカー・ピン**

- 色はすべてCSSトークンで管理する(ハードコード禁止):
  - `--map-marker-destination`(目的地): 赤系だが彩度を抑えたモダンな赤(#e0524d 系)
  - `--map-marker-current`(現在地): 青系(#1769aa 系を維持)
  - `--map-marker-focus`(注目地点): アクセント(`--color-accent`)
- イベントバッジは軽量な円形バッジ(白地 + teal縁 + 人型グリフ、画面上直径 22〜26px)とし、現在の黒い矩形バッジ(1.6xスケール)は廃止する
- **ズーム連動の表示制御**: キャンパス全体シートでは個別イベントマーカーを出さず、**建物単位に集約したバッジ(イベント件数付き)**を建物アンカーに表示する。建物シート(フロア表示)では地点ごとの個別バッジを表示する。集約バッジのタップは建物タップと同じ挙動(該当建物シートへの切替)とする
- 既存ルール(同一地点の複数イベント集約、現在地・目的地・注目ピンとの重複時はイベントマーカー省略)は維持する

### 3.2 現在地と目的地

アプリの中心状態は「現在地」と「目的地」の2つ。どちらもURLで表現する(5.2)。

**目的地のセット**
- アプリ内: イベント検索 → 詳細 → 「ここへ行く」
- 外部から: チラシ・公式サイト等に貼られたリンク(`/e/:eventId` 等)を踏むと、目的地セット済みでアプリが開く

**現在地のセット**
- 会場各所に貼られた**URL型QR**。中身は `アプリURL + QR ID`(例: `/q/Q012`)。スマホ標準カメラで読むとブラウザでアプリが開き、現在地がセットされる
- **QRは地点IDを直接持たない**。QR ID → Place の対応表(バックエンド管理)で解決する。これによりQRの貼り替え・再割当を印刷し直しなしで行える。対応表には固定(常設掲示)/可変(当日掲示)の種別カラムを持たせる
- **アプリ内スキャン**も提供: QRタブからカメラを起動し、アプリを開いたまま同じQRを読める(目的地を保持したまま現在地だけ更新される、が重要)

**挙動**
- 目的地のみ → 地図が目的地にフォーカス(マーカー表示)
- 現在地のみ → 地図が現在地にフォーカス
- 両方セット → **ルート表示**(3.3)

### 3.3 ルート表示(コア機能)

- 構内の歩行経路を**経路グラフ**(ノード = 通路上の点・階段・出入口、エッジ = 歩行区間)としてデータで持つ
- ルート計算はフロントエンドでDijkstra等のグラフ探索を行う(この規模ならクライアント側で十分。バックエンド不要)
- 建物間は屋外歩行者路、建物内は廊下・階段を通る。フロア・シートをまたぐ接続(階段、建物出入口)はグラフのエッジとして表現する
- 階段接続のv1方式: 同じ物理階段を指す各フロアの階段ノードに共通の `data-stair-id` を付け、抽出スクリプトが隣接フロアのペアごとに固定コストの**transferエッジ**を自動生成する。SVGにはフロアをまたぐpathを描かない(作図規約は [MAP_AUTHORING.md](MAP_AUTHORING.md) の「階段接続」)
- 表示: 現在フォーカス中のシート/フロア上のルート区間を線でハイライト。フロアをまたぐ箇所は階段ノード位置に乗換マーカーを表示する。ルートが別フロア・別建物へ続く場合はフロア切替UIと連動する(v1はルートが通るフロアの切替ボタンにインジケータを表示)
- 区間ごとのテキスト案内(「階段で2Fへ」等)は将来拡張とし、v1はルート線の表示まで

**経路グラフの作成方法**: 各SVGに `Route` レイヤーを追加し、歩行経路をポリライン(path)で描く。
命名規則付きノード(階段・出入口・QR地点)を含め、**ビルドスクリプトがSVGを解析してグラフJSONを生成**する。
地図の見た目と経路データが同じファイルで管理され、地図修正時のズレを防げる。

- 作図ツールはInkscape/Illustratorどちらでも良い。契約は「書き出したSVGにレイヤー名と要素IDが生き残ること」のみ。ID・レイヤー名はASCII英数字とし(Illustratorの `_x30_` エスケープ回避)、抽出スクリプトがID検証を行い壊れていればエラーで検知する
- 既存9ファイルはInkscape製のため、Illustratorで開いて上書き保存するとID群が再構成される恐れがある。既存ファイル編集後は抽出スクリプトの検証を通すこと
- 経路計算・経路グラフは**フロントエンドの持ち物**であり、バックエンドに経路APIは作らない(グラフはSVG由来でフロントの座標系に属するため。二重管理と当日の回線不安リスクを避ける)

### 3.4 イベント検索(Event Search)

- テキスト検索 + タグ(カテゴリ)フィルタでイベントを絞り込む
- **検索はフロント側で実行**する: 起動時にイベント全件(数十件規模)を取得し、クライアントで絞り込む。検索APIは作らない(入力ごとに即応答でき、当日の回線不安にも強い)
- イベントカードをタップすると**イベント詳細画面**を開く
- 詳細画面の「ここへ行く」で目的地セット → 地図へ
- **強調表示**: `/events?highlight=:eventId` で開くと該当イベントカードを視覚的に強調し、リスト内のその位置までスクロールする(地図のイベント開催地マーカーのタップ先。3.1)。highlight中も検索・絞り込みは通常通り操作できる。既存の `at`/`to` クエリは保持する

### 3.5 イベント詳細

- 表示内容: タイトル、時間帯、場所、タグ、説明文(詳細は Figma iPhone 17 - 5 の再構築時に確定)
- 「ここへ行く」→ 目的地セット

### 3.6 スケジュール(Schedule)

- **v1**: 公式タイムテーブルPDF(画像化したもの)をそのまま表示
- **将来**: イベントデータと連動したタイムライン表示に差し替える。
  そのため、イベントデータには最初からタイムライン描画に足りる時間情報(開始・終了・休憩等)を持たせる

### 3.7 スコープ外(v1では作らない)

- ブックマーク / マイスケジュール機能
- ユーザーアカウント・ログイン
- スタンプラリー等のゲーム要素
- リアルタイム混雑度
- GPS等による自動測位(現在地はQRのみ)

## 4. データモデル

バックエンドは自分でこれから作る。**API契約はフロント側から先に定義**し、
バックエンドはそれに合わせて実装する(契約は [API.md](API.md))。

役割分担:
- **バックエンド**: イベント・場所対応・QR対応表の管理と配信(登録・編集のしやすさが価値)
- **フロントエンド**: 地図SVG・経路グラフ(SVG由来の静的アセット)、経路計算、検索の実行

```
MapSheet  … SVGファイル1枚(id, name, svgUrl)。キャンパス全体図 or 建物図
Floor     … シート内のフロア領域(id, sheetId, name)。LHのように1シート複数フロアがある
Place     … 地点(id, floorId, svgElementId または座標, name)
             ← QRの地点ID・イベント会場・建物出入口はすべてPlace
Event     … イベント(id, title, description, placeId, tags,
              timeSlots: [{start, end}] ← 複数回開催・休憩を挟む場合は複数スロット)
Tag       … カテゴリ(id, label)
QrCode    … QR対応表(qrId, placeId, 種別: 固定/可変, 設置場所メモ)
RouteNode … 経路ノード(id, floorId, x, y, 種別: 通路点/階段/出入口)
RouteEdge … 経路エッジ(nodeA, nodeB, 距離)。フロア間・シート間接続もエッジで表現
```

- `MapSheet / Floor / Place / RouteNode / RouteEdge` はSVGから生成する静的データ
- `Event / Tag / QrCode` はバックエンド(完成まではモック)から取得
- ステップ1の仮Placeは `mapping: unmapped` を明示して位置アンカー未確定を許容する。ステップ2で全地点をSVG要素または座標へ解決し、未紐付けを検証エラーにする
- **Event.id は公式タイムテーブルの記号をそのまま使う**(例: `A1` 大学説明会, `L1`・`L2` 入試説明会, `P1` 研究室公開, `M21` 体験授業, `R3` 受験勉強相談, `G1` なんでも相談会, `T1` キャンパスツアー)。外部リンク `/e/L1` がそのまま人間にも読める。公式記号がないイベントは衝突しない英小文字slug(例: `campus-free-tour`)を定義する。複数回開催は公式に別記号があれば別Eventとし、休憩を挟む開催はtimeSlotsの複数要素で表現する
- `timeSlots` を配列にするのは「10:00〜15:00(休憩12:00〜13:00)」のような帯とスケジュールタイムライン化(3.6)の両方に対応するため
- 年度更新はイベントデータとQR配置の総入れ替えで行う(スキーマは年度非依存に保つ)

## 5. 技術方針

フロントは React 19 + TypeScript + Vite(既存構成を踏襲)。パッケージ管理は bun。

### 5.1 データ取得層

- UIコンポーネントは直接fetchしない。`src/data/`(リポジトリ層)を介してデータを取得する
- v1開発中はモックデータ実装(静的TSファイル)で全画面を動かし、バックエンド完成後にAPI実装へ差し替える。差し替えはこの層の中だけで完結させる

### 5.2 ルーティング(URLを状態にする)

現在地・目的地はURLで表現し、「URLを開けば同じ状態が再現される」ことを基本品質とする:

- `/` … 地図(デフォルト)
- `/q/:qrId` … 現在地セット(**QRのリンク先**)。QR対応表でPlaceに解決。目的地が既にあればルート表示
- `/p/:placeId` … 地点フォーカス(アプリ内部での地点表現)
- `/e/:eventId` … 目的地セット(**外部リンクのリンク先**)兼イベント詳細。例: `/e/L1`
- `/events` … 検索
- `/qr` … アプリ内QRスキャン
- `/schedule` … スケジュール

React Router v7をSPAライブラリモードで使用する。アプリの中心状態は次のクエリで表す:

- `at=:placeId` … QRで解決した現在地
- `to=:eventId` … 選択した目的地イベント
- `focus=:placeId` … 現在地とは独立した地図の注目地点

`/q/:qrId` はQRを解決して `/?at=:placeId` へ、`/p/:placeId` は
`/?focus=:placeId` へ正規化する。既存の `to` は保持する。
`/e/:eventId` は有効なイベントなら `to=:eventId` をURLへ反映し、詳細を表示する。
検索・QR・スケジュールのタブ移動ではこれらのクエリを保持する。
`/`・`/p/*` は地図画面として3タブのいずれも選択状態にしない。
本番のSPAフォールバック、Viteの`base`、Routerの`basename`はホスティング先の確定時に設定し、
`/q/*`・`/e/*`の直接アクセスを本番環境でも検証する。

### 5.3 地図・経路の実装方式

- SVGはfetchしてインラインDOMとして描画(要素ID操作・CSSハイライトのため)
- パン・ズームはviewBox操作で自作、複雑化するならライブラリ導入を検討
- 経路グラフはビルド時にSVGの `Route` レイヤーから抽出したJSONを読み込み、探索(Dijkstra)はクライアントで実行

### 5.4 ディレクトリ構成(feature単位)

```
src/
  app/        … ルーティング・全体レイアウト(シート+地図の骨格)
  features/
    map/      … SVG地図描画、シート/フロア切替、マーカー、フォーカス制御
    routing/  … 経路グラフ、ルート探索、ルート描画データ生成
    events/   … 検索パネル、イベント詳細
    qr/       … QRパネル、アプリ内スキャン
    schedule/ … スケジュールパネル
  components/ … 汎用UI(BottomSheetなど feature に属さないもの)
  data/       … リポジトリ層(モック実装 → API実装)、エンティティ型定義
  styles/
scripts/      … SVG→経路グラフJSON抽出などのビルドスクリプト
public/maps/  … 地図SVGアセット
```

既存の `src/components/bottom-sheet/` 内の各パネルは、この構成への移行時に各featureへ振り分ける。

## 6. 開発ロードマップ

縦切り(画面ごとにUI+処理をセットで完成)で進める。

1. **土台**: データモデル型定義 + モックデータ + リポジトリ層 + React Router導入 + feature構成への再編
2. **地図表示**: SVGインライン描画・パン・ズーム・シート/フロア切替・地点フォーカス・マーカー
3. **ルート**: `Route` レイヤーの作図規約決定 → 抽出スクリプト → 探索 → ルート線描画(まず研究棟1フロア内、次に階段・屋外またぎ)
4. **イベント検索**: 実フィルタリング + 詳細画面 + 「ここへ行く」接続
5. **QR/ディープリンク**: `/p/:placeId`・`/e/:eventId` 対応 → アプリ内スキャン
6. **スケジュール**: PDF画像表示
7. **API接続**: API契約確定(`docs/API.md`)→ バックエンド実装 → リポジトリ層差し替え
