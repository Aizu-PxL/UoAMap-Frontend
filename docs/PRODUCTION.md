# 本番公開・デプロイ・実機QR受入計画

最終更新: 2026-07-21

## 位置づけ

本番URLの決定、ホスティング設定、バックエンド接続、QRの印刷・設置、実機受入、当日運用を一つの手順で管理する。
アプリの機能仕様は [SPEC.md](SPEC.md)、API契約は [API.md](API.md)、通常の実装・検証手順は [WORKFLOW.md](WORKFLOW.md) を正とし、この文書は**公開作業と現地受入の正**とする。

現時点では計画のみで、ホスティング先・本番URL・QR設置一覧は未確定。本番公開済みではない。

## 1. 公開の基本方針

- QRにはPlace IDを直接入れず、確定した本番URLの `/q/:qrId` を入れる。
- 本番URLは年度が変わっても使い続ける。年度や開催日をパスへ含めない。
- 推奨は大学が管理できる専用サブドメインのルート配下（例: `https://map.example.ac.jp/`）。`/uoamap/` のようなサブパス配信は、組織の制約で必要な場合だけ採用する。
- 本番はHTTPS必須。アプリ内QRスキャンのカメラ利用にはsecure contextが必要。
- `/q/*`、`/e/*`、`/p/*` への直接アクセスをSPAのエントリへ戻すフォールバックが必須。
- QRの量産印刷は、本番origin・base path・リダイレクト方針を凍結し、実印刷サンプルの実機受入がPASSしてから行う。
- フロントに秘密情報を埋め込まない。公開読み取りAPIの接続先だけをビルド設定または同一originの `/api` で与える。
- QR印刷後に本番originを変更しない。やむを得ず変更する場合は、旧URLを長期リダイレクトし、アプリ内スキャンの同一origin判定も再検証する。

## 2. 人間と実装担当の役割

| 項目 | 主担当 | 内容 |
|---|---|---|
| 公式URL・ドメイン承認 | 人間（大学・運用責任者） | 利用可能なドメイン、所有者、継続年数、DNS変更権限を確定 |
| ホスティング契約・組織設定 | 人間 | 組織アカウント、請求、管理者、リポジトリ連携、デプロイ権限を設定 |
| DNS・証明書 | 人間 | CNAME等のDNS設定、HTTPS証明書の発行・更新、期限監視を確認 |
| バックエンド運用 | 人間 + バックエンド担当 | API本番環境、データ更新権限、CORSまたは同一originプロキシ、障害対応を用意 |
| フロント設定・テスト | 実装担当 | Vite `base`、Router `basename`、SPAフォールバック、APIリポジトリ、検証を実装 |
| QR台帳・印刷・設置 | 人間（会場運用担当） | qrId採番、設置場所、印刷版、掲示、撤去、差し替えを管理 |
| 実機受入 | 人間主体、実装担当補助 | iPhone/Android、標準カメラ、アプリ内スキャン、現地回線・照明で確認 |
| 公開・中止判断 | 人間（リリース責任者） | Go/No-Go、ロールバック、当日掲示の扱いを決定 |

Codex等の実装担当だけでは、公式ドメインの取得・DNS変更・外部サービスの所有者決定・物理QRの印刷設置・現地での最終合否判定は完了できない。

| 本番デプロイ元ブランチ | 未定 | ⬜ |
| デプロイ承認者・実行者 | 未定 | ⬜ |
| バックエンドoriginまたは同一origin `/api` の構成 | 未定 | ⬜ |
| DNS・証明書の管理者 | 未定 | ⬜ |
| ロールバック実行者 | 未定 | ⬜ |
| QR台帳・印刷・設置の責任者 | 未定 | ⬜ |
| 当日のGo/No-Go責任者 | 未定 | ⬜ |

### URLの正規形

値の凍結時に、次の実URLを台帳へ記録する。

```text
アプリトップ:     <production-origin><base-path>
QR:               <production-origin><base-path>q/<qrId>
イベント外部導線: <production-origin><base-path>e/<eventId>
地点確認用:       <production-origin><base-path>p/<placeId>
```

base pathは `/`、または `/uoamap/` のように先頭・末尾を `/` に揃える。`www`有無、HTTP→HTTPS、仮ホスト名から本番ホスト名への転送も統一する。印刷QRには転送前の仮URLではなく、利用者に保証する正規URLを格納する。

## 4. ホスティング選定条件

特定サービス名ではなく、次をすべて満たすことを採用条件とする。

- カスタムドメインと自動更新されるHTTPS証明書
- Viteの静的成果物 `dist/` の配信
- `/q/*`、`/e/*`、`/p/*`、`/events`、`/qr`、`/schedule` のSPAフォールバック
- プレビュー環境と本番環境の分離
- 直前の正常デプロイへ短時間で戻せること
- デプロイ履歴、実行者、ビルドログを確認できること
- DNS・プロジェクト・リポジトリ連携が個人アカウントに閉じないこと
- 必要なら `/api/*` をバックエンドへ同一originで転送できること。別originの場合は [API.md](API.md) のCORS条件を満たすこと
- `THIRD_PARTY_NOTICES.txt` を含む `dist/` を欠落なく配信できること

GitHub Pages、Vercel等の候補比較は、この条件と大学側のアカウント・DNS・保守方針が揃ってから行う。サービスを決める前にQR URLを確定しない。

## 5. 実装計画

### Phase A — URL・運用設計（人間必須）

1. §3の未定項目を確定する。
2. QR設置地点一覧とqrId採番規則を確定する。
3. 固定QRと当日差し替え可能なQRを区別し、バックエンドの対応表更新権限を決める。
4. 本番障害時に「旧デプロイへ戻す」「QR解決だけ差し替える」「掲示を停止する」の誰が何を行うか決める。
5. 本番URLの凍結をリリース責任者が承認する（Gate 0）。

### Phase B — デプロイ実装（実装担当）

1. ホスティング設定とSPAフォールバックを追加する。
2. ルート配信ならVite `base=/` を維持する。サブパス配信ならVite `base` とReact Router `basename`を同じbase pathへ揃える。
3. [API.md](API.md) の実装を `src/data/` のリポジトリ層へ追加し、モックと本番APIの切替方法を明示する。
4. APIが別originなら許可originを本番・プレビューに限定する。同一origin `/api` を使えるならそれを優先する。
5. カメラを拒否する `Permissions-Policy` やiframe制約が入っていないことを確認する。
6. 本番ビルド手順を固定する。基準は依存関係をロックした上での `bun run build`。
7. ステージングへ自動または承認付きでデプロイし、デプロイ手順とロールバック手順を記録する（Gate 1）。

実装時は [WORKFLOW.md](WORKFLOW.md) に従い、API接続、ホスティング設定、公開受入を必要に応じて小さいスライスへ分け、各スライスのSCOPEと受入基準を持つ `docs/tasks/` のブリーフを先に作る。

### Phase C — ステージング受入

最低限、次をステージングの実URLで確認する。

```bash
bun test
bun run build
bun run verify:places
bun run verify:routes
git diff --check
```

- トップと全ディープリンクを、アプリ内遷移ではなくアドレスバーへの直入力・再読み込みで開ける。
- `at` / `to` / `focus` がタブ移動・直接リンク・再読み込みで保持される。
- `GET /api/events`、`GET /api/tags`、`GET /api/qrs/{qrId}` が契約どおりに応答する。
- 存在しないQRで `QR_NOT_FOUND` 相当の利用者向けエラーになる。
- HTTPS、証明書、リダイレクト、主要静的アセット、地図SVG、スケジュール画像、QR Worker、第三者通知が配信される。
- 幅320px / 402px / 430pxで横スクロールや操作不能がない。
- iOS SafariとAndroid Chromeの少なくとも各1台で、標準カメラとアプリ内スキャンを確認する。
- ステージングのアプリ内スキャンにはステージングoriginの検証QRを使う。本番QRは本番origin上で受入する（同一origin判定のため）。

すべてPASSしたデプロイだけを本番候補とする（Gate 2）。

### Phase D — 本番デプロイと実印刷サンプル

1. Gate 2と同一のコミット・成果物を本番へ昇格する。
2. 本番URL、HTTPS、SPA直リンク、API、主要ルートをスモークテストする。
3. 本番URLを格納したQRを、実際に使う用紙・サイズ・印刷機で少数だけ印刷する。
4. 実際の掲示位置、照明、読み取り距離、角度、反射、通信状態で§6の実機受入を行う。
5. 実印刷サンプルがPASSしたらURLとQR内容を最終凍結する（Gate 3）。
6. QRを量産し、台帳と照合しながら設置する（Gate 4）。

### Phase E — 当日運用

- 開場前にトップ、代表3地点以上のQR、代表イベント、建物間ルート、アプリ内再スキャンを確認する。
- QR対応表の最終更新時刻とキャッシュ反映を確認する。
- 障害時は、利用者影響を優先して旧デプロイへのロールバック、QR対応の修正、掲示停止を選ぶ。
- 終了後、可変QRの撤去、固定QRの保管、インシデントと翌年度向け改善点を記録する。

## 6. 実機QR受入

### 6.1 使用端末

最低限、次の2系統を実機で確認する。可能なら来場者層に近い旧端末も1台追加する。

- iPhone + Safari + 標準カメラ
- Android + Chrome + 標準カメラ

端末名、OS、ブラウザ版、実施日時、回線、担当者を証跡へ残す。PCのWebカメラやQR画像ファイルだけの確認は最終受入の代替にしない。

### 6.2 受入シナリオ

| # | 操作 | 期待結果 |
|---|---|---|
| QR-01 | 標準カメラで固定QRを読む | 本番 `/q/:qrId` が開き、正しい `at` へ正規化される |
| QR-02 | 目的地なしでQRを読む | 現在地ピンが表示され、地点名が台帳と一致する |
| QR-03 | `to` 設定後にアプリ内でQRを読む | `to` を保持し、`at` だけ更新してルートを表示する |
| QR-04 | QRタブへ戻り別QRを読む | 旧 `focus` を削除し、目的地を保持したままルートを再計算する |
| QR-05 | 無効・未登録QRを読む | クラッシュせず日本語エラーとスタッフ案内を表示する |
| QR-06 | カメラ権限を拒否後に再試行する | 日本語の復旧案内が出て、権限復旧後に再開できる |
| QR-07 | 外部originや別パスのQRをアプリ内で読む | 道案内QRとして受理せず、スキャンを継続する |
| QR-08 | `/q/*` を新規タブ・再読み込みで開く | 404にならず、同じ地点へ解決する |
| QR-09 | 弱い回線でQRを読む | 待機中・失敗が判別でき、再試行またはスタッフ案内へ進める |
| QR-10 | QR対応表を変更する | 定めたキャッシュ時間内（API契約上は60秒以下推奨）に新しいPlaceへ解決する |
| QR-11 | 実掲示位置から読む | 想定距離・角度・照明・反射の範囲で両OSが読み取れる |
| QR-12 | 代表ルートを最後まで確認する | 現在地・目的地・階段/建物間の表示が公式会場配置と一致する |

### 6.3 QR台帳

QRは最低限、次の列を持つ台帳で管理する。CSV、スプレッドシート、バックエンド管理画面のどれを正にするかは人間が決める。

```text
qrId
productionUrl
placeId
kind (fixed / variable)
installationNote
physicalLocation
printRevision
printedAt
installedAt
removedAt
acceptedDevices
acceptanceResult
owner
notes
```

QR画像ファイル名にも `qrId` と印刷版を含め、台帳上のURLと画像を目視・機械の両方で照合する。QR画像を作り直した場合は旧版を現場へ混在させない。

### 6.4 受入証跡

各シナリオについて次を残す。

- PASS / FAIL
- 実施日時・担当者
- 端末・OS・ブラウザ・回線
- qrId・期待Place・実際のURL
- 必要に応じて画面録画または写真
- FAIL時の再現手順、利用者影響、修正版の再受入結果

## 7. Go / No-Go基準

次をすべて満たした場合のみ量産・本番案内をGoとする。

- [ ] §3の所有者・URL・デプロイ・ロールバック項目が確定している
- [ ] 本番URLが大学側で承認され、HTTPSが正常
- [ ] 本番でトップと全ディープリンクの直接アクセスがPASS
- [ ] 本番APIとQR対応表が [API.md](API.md) に適合
- [ ] `bun test`、build、places、routes、diff checkがPASS
- [ ] iPhone / Androidの標準カメラとアプリ内スキャンがPASS
- [ ] 実印刷・実掲示条件で代表QRがPASS
- [ ] QR台帳と印刷物が一致し、未登録・重複・旧版混在がない
- [ ] ロールバック手順を担当者が実行可能
- [ ] 当日担当者と連絡経路が決まっている

1つでも満たさない場合はNo-Go。期限だけを理由にQRの量産や本番案内を先行しない。

## 8. ロールバックと変更管理

- フロント不具合: 直前の正常デプロイへ戻す。新しい修正を本番上で直接作らない。
- QR対応誤り: バックエンドのQR対応表を修正し、キャッシュ反映後に該当QRを再受入する。
- 本番URL/DNS障害: 人間のDNS管理者とホスティング管理者が対応する。印刷済みQRを救済できる旧URLリダイレクトを維持する。
- 会場配置変更: `placeId`の再割当だけで正しく案内できる場合はQR対応表で処理する。地図・Route・Place自体が変わる場合は通常の実装・検証ゲートへ戻す。
- すべての本番変更について、実行者、日時、対象、理由、確認結果を記録する。

## 9. 完了条件

この計画の完了は、単にデプロイURLが開くことではない。次が揃って完了とする。

1. URL・所有者・ホスティング・API・ロールバックの決定記録
2. 再現可能なデプロイ設定と正常な本番デプロイ
3. SPA直リンク、API、主要機能の本番受入
4. QR台帳、実印刷サンプル、iPhone/Androidでの実機受入証跡
5. 量産・設置確認と当日運用責任者のGo承認
